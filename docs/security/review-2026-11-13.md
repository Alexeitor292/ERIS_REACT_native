# Security review — November 13, 2026

**Decision: source handoff is being prepared; production security acceptance is
not complete.** Project owner: **Deh Jeng Jang**. This review covers the
repository and local disposable builds, not a penetration test or inspection of
the personal staging host or future Caltrans infrastructure. There is no
defensible guarantee of zero risk. Known dependency advisories, source findings,
runtime-image findings and deployment controls are separate evidence streams.

## React and the deployment boundary

ERIS builds a client-side React/Vite bundle and serves static files with nginx.
The production web container has no Node/Vite development server or React
Server Components endpoints. FastAPI is the application server. The locked
web dependency tree has no `next` or `react-server-dom-*` package. This excludes
the specific RSC attack surface described in the linked React advisories; it
does not prove immunity to XSS, authorization bugs or other dependency issues.
[React's RSC advisory scope](https://react.dev/blog/2025/12/11/denial-of-service-and-source-code-exposure-in-react-server-components).

Retain React's escaping, sanitize stored rich text on both server (`nh3`) and
client (`DOMPurify`), keep session credentials HttpOnly and enforce API role/
record checks. Replacing React alone would not remove the Python, OS, storage,
database, identity or operational patching responsibilities.

## Changes made in this handoff

- Added `backend/constraints.txt` from the fresh Linux worker resolution so API
  and worker transitive dependencies do not silently drift on rebuild. Direct
  requirements remain readable; change constraints and audit together.
- Updated the nginx runtime baseline from 1.27 to a verified, pinned 1.30.6
  image, applying available Alpine security packages during build. API/worker
  builds apply available Debian updates and explicitly update pip.
- Worker runs as UID/GID 10001. API/worker Podman and Compose launches drop all
  Linux capabilities and prohibit privilege escalation. API currently retains
  container UID 0 so it can read existing host-owned mode-600 certificate/APNs
  mounts; see the remaining container gate below.
- The road geometry hash is explicitly non-security SHA-1 to preserve existing
  stable identifiers; package integrity and credentials continue to use their
  existing security algorithms. No integrity protection was downgraded.
- Corrected Compose browser routing to same-origin `/api` and the separate
  container's `backend:8000` upstream; hosted examples use HTTPS and local
  web/API binds instead of the old cross-origin/plain-HTTP settings.
- Release image scanning now defaults to **all severities**, including findings
  without fixes. It no longer uses `--ignore-unfixed`. npm CI likewise fails on
  low-and-higher advisories. No CVE exceptions were added to `.trivyignore`.
- Added a daily/manual/PR security workflow with dependency, high-confidence
  high-severity Bandit, and redacted Git-history secret checks. It retains full
  Bandit findings for human review. Added weekly Dependabot update proposals
  for npm, Python, Docker and Actions. Exact Swift versions in XcodeGen still
  require maintainer review; the empty-dependency ERISKit package cannot update
  the separate XcodeGen MSAL/ArcGIS pins automatically.
- Added [candidate vendor image recipes](../../deploy/images/README.md) to
  address the MariaDB helper's old Go toolchain and SeaweedFS dependencies.
  These must be built, scanned, functionally accepted, mirrored and signed by
  the agency; a Dockerfile is not evidence of an approved runtime release.

## Secret-scanner metadata disposition

A subsequent Git-diff scan flagged 109 values in the newly committed **raw image
reports**: 91 public content/revision hashes and 18 public upstream GPG/PGP
signing-key fingerprints. Each was checked as hexadecimal public metadata,
not an application credential. `.gitleaksignore` records only their exact
commit/path/rule/line fingerprints from commit `323b2b4`; it does not exempt
application paths, report directories or future commits. Updates must be
reviewed again. This is separate from `.trivyignore`, which has no accepted CVEs.
The security workflow explicitly loads this reviewed fingerprint list.

## Static-source triage

Bandit's initial high finding was SHA-1 used for deterministic **road geometry
IDs**, not password hashing, signing or integrity; marking it
`usedforsecurity=False` addresses the incorrect cryptographic classification
without renaming existing road IDs.

98 medium findings are low-confidence SQL string-construction signals. Reviewed
examples use bound values with fixed SQL fragments/placeholders and known
column names (including Pydantic fields and crack-field allowlists). They are
not automatically SQL injection. The complete finding list remains available
for independent tracing of each interpolation and caller before security
sign-off. No blanket SQL suppression or claim of exhaustive manual clearance
has been added.

Other signals include certificate SHA-1 **display thumbprints** (the actual
Entra client assertion uses PS256/SHA-256), configured upstream `urlopen` calls,
network bind defaults, retry jitter, ordinary `bearer` string literals, and
exception handling. Review configured endpoints/redirect behavior, resource
limits and error handling in the deployment threat model. Scanner severity
alone does not establish reachability or authorize an exception.

## Reproduce and accept

```bash
# Repo root, with the backend virtualenv active:
pip install pip-audit==2.10.1 bandit==1.9.4
pip-audit -r backend/requirements-worker.txt --format json --output python-audit.json
bandit -r backend/app --severity-level high --confidence-level high
cd web
npm ci
npm audit --audit-level=low
npm test
npm run build
```

Use `.github/workflows/security.yml` for full redacted secret/history and
static-report reproduction. Use `deploy/ci/release-gate.sh scan` on each **built
image** for deployment evidence; source scans cannot see all OS/native-library
packages. Archive reports, image digests and database revision with the release.
The strict default gate currently blocks deployment on the remaining reported OS findings and can intentionally block deployment while vendor fixes
or approved exceptions are outstanding. Operational acceptance remains in the
[handoff record](../handover/acceptance.md), not implied by this dated assessment.
