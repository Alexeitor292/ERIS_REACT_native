The review followed callers, input origins, authorization and failure handling.
It found two concrete security problems, corrected below. The other findings

This is a scoped source review and regression testing, **not** a penetration test,
agency security approval or evidence that the application has zero risk.

## Problems found and corrected

1. **Photo ingestion read before authorization and the upload limit.** The
   metadata wrapper read the whole upload before the actual storage function
   checked form edit permission and performed its bounded read. It also
   swallowed rewind failures. Removed the wrapper and its installation hook.
   [`photos.py`](../../backend/app/photos.py) now checks permission, reads at
   most `MAX_UPLOAD_MB * 1024 * 1024 + 1`, rejects empty/oversized content, then
   parses optional EXIF from those same bytes. It never rewinds or reads again.
   The three [regressions](../../backend/tests/test_photo_upload_limits.py)
   failed before the fix and pass afterward: unauthorized content is not read
   or parsed; oversized content is rejected before parsing; valid content and
   fallback metadata survive a single bounded read. Multipart reception and
   aggregate traffic still require the documented gateway size/rate controls.
2. **SMTP TLS did not authenticate the relay.** Reviewing the SMTP cleanup
   finding exposed implicit TLS and STARTTLS calls without an explicit verified
   context. Both now use `ssl.create_default_context()`, requiring certificate
   and hostname verification. TLS failure propagates before credentials or
   messages are sent; there is no downgrade when STARTTLS is unavailable.
   Production/staging settings also reject authenticated SMTP without TLS.
   [SMTP regressions](../../backend/tests/test_notification_smtp.py) cover both
   TLS modes, certificate/handshake failures and unsupported STARTTLS. An
   explicitly selected unauthenticated plaintext internal relay remains an IT
   policy decision. Private relay CAs belong in the approved container trust
   store; do not disable verification to accommodate them.

Focused upload/metadata tests: **26 passed**. The full local non-DB suite after
the upload and SMTP-context changes: **1,484 passed, 761 deselected**. The final
SMTP production-setting addition has separate focused session/SMTP/template
coverage: **154 passed**. The final committed combination passed **1,494 non-DB**
and **761 DB** tests in CI; the latter also passed against the exact patched
MariaDB candidate.

## URL and deployment boundary retained for agency acceptance

The five B310 calls do **not** take a destination URL directly from an HTTP
request. Four use trusted server configuration and one uses a fixed source
constant. That establishes their input boundary; it is not a general SSRF
allowlist. `urllib` redirect behavior and DNS/network reachability remain active,
and these functions do not themselves enforce an approved-host policy.

For the selected deployment, record the actual postmile/3DEP destinations and
any redirect destinations, approve their schemes/hosts, and restrict service
account egress and proxy access accordingly. Do not put unreviewed URLs into
runtime settings. Verify the rules on agency staging. Leave Expo delivery off
for the native-only rollout unless separately approved. These are concrete
configuration/network acceptance checks, not deferred disposition of an unknown
user-controlled URL.

The exception review found no remaining exception handler among these findings
that treats failed authentication or a failed permission check as success.
It does identify incomplete enrichment, delivery, job-status reporting and
best-effort deletion as operational outcomes that need the existing
[acceptance record](../handover/acceptance.md), retention decisions and monitoring.
No scanner rule/file suppression was added for these findings.
