## 1. Executive summary

**The problem in numbers.** On a 375×812 phone the first **700 px** of `/my-work`, `/incidents` and `/assessments` is navigation. On a 768×1024 iPad — the primary field device — the same: a 577 px nav card, then an 860 px rail, then the detail. The Staff technical form (`/submissions/3`) is **11.1 screens tall** on a phone with **180 overflowing elements**, **120 targets under 40 px**, **74 text nodes under 12 px**, and 520 px-wide cards in a 375 px viewport; at 1440 it degrades to one 520 px column 3,802 px tall. Of 15 first-day tasks walked through with no training, **4 were blocked and 4 confusing**; only 7 worked. Underneath is one cause: a newcomer must learn **five numbered objects** (Incident, Event Group, Assessment, Submission, cross-section Project) across **six read-only record pages plus a separate action inbox** before doing anything. Every failed walkthrough failed at the same question — *"which of these four pages holds the status of an incident?"*

**The direction: Inbox + Case file.** The judges split two-two on the backbone (case-file 34.3, task-first 34.5 across four reviews — a dead heat; see Appendix B for the file paths and the scoring criterion) but all four converged on the same hybrid and all four rejected map-first as an architecture while wanting its map engineering. Two halves:

- **A personal Home for every role — including the reporter.** Not a filter — a place. Grouped by the action you must take, nothing vanishes silently, every row leads with the site ("District 7 · Los Angeles · Route 101 · PM 12.30"), not three internal ids.
- **One role-aware case file per incident.** `/incidents/:id` becomes the only record page. Assessment, technical form, evidence, site and history become **tabs**, not destinations. No backend object is renamed and no transition changes; the objects stop being places you navigate to.

Navigation collapses from seven sidebar entries to **at most four destinations per role**: Home · Records (Incidents · Event Groups · Assessments as segments) · Map · one role-specific fourth (Admin, or Terrain for Staff and senior engineers). The same four render as a bottom bar on phones, an 80 px labelled rail on iPads and a 256 px sidebar on desktops — the mental model never changes, only the container. Every hand-off becomes a **route-backed guided flow** (`/assessments/:id/delegate`) that renders as a full page on a phone and a dialog from `md` from one implementation, states the consequence before the button, holds that action's note, and leaves a receipt.

**What changes per role.** *Reporter*: a real Home with **Needs your update / Filed and waiting / Recently accepted**, plain statuses, the actual fields a coordinator wants fixed, and a route-backed **Update your report** flow that closes the loop the coordinator opens. *Coordinator*: one Review-report flow instead of two dialogs with two commit buttons and a pre-checked nearest Event Group; triaged reports move to "Recently accepted" instead of vanishing; district filters everywhere; the map plots incidents. *Office chief*: Home grouped **To route / To review**, office-scoped so nothing 403s; incident context inline; Records › Assessments gives per-state counts and "longest in this step". *Branch chief*: **you approve the assessments handed to you** — no reviewer to assign and no sign-off after; the Staff picker shows branch, office and open-assessment load. *Staff*: the drag-and-resize canvas becomes a section task list with autosave, the reviewer's comment quoted first, one Submit that advances both records, 3D on request — and, until web upload is callable, a written notice that photos come from the mobile app. *Senior engineer*: a new role that fills assessments the office chief assigns directly and returns them to that chief. *Admin*: "Assigned to me" by default with an "All queues" toggle, plus a System-health strip surfacing districts with no coordinator.

**Roadmap.** Seven phases, **73 working days of calendar** for a team of **two front-end engineers, two backend engineers full-time for Phase 1 and then one at roughly a third of their time, a designer at half time, and QA at half time from Phase 3** — 137 front-end engineer-days and 37.75 backend engineer-days, itemised per phase in §11. Each phase after Phase 0 is independently shippable because routes never move. Phase 0 (14 d) is the only global change — AppShell as a layout route with bottom bar / rail / sidebar, the status-and-role vocabulary as one pure label module, the shared primitives, the Not Found screen, and a **build-time** feature flag. Phase 1 (11 d) delivers Home for all seven roles, routing v2 and the routing flows. Phase 2 (12 d) builds the case file, merged triage, the reporter's update flow and web intake on a new `GET /incidents/{id}/case` aggregate. Phase 3 (14 d) is the technical form — the risky phase, behind the flag with a GISA parity checklist. Phase 4 (8 d) Map and Terrain. Phase 5 (7 d) Records and Admin. Phase 6 (7 d) accessibility, cross-client labels and the QA matrix.

**Three backend items gate**: B1 (one transaction driving assessment *and* submission), B12 (the queue filters Home's groups are built from) and B3 (the case aggregate) — and **two new ones, B15 (routing v2) and B16 (the approval email), gate Phase 1 with them**. Of the two items previously listed as backend work, **B2 is moot: there is no finalize list**, and B10 (the reporter's requested fields) **already ships server-side** and is client-only work; §11 says so and re-costs them.

## 2. What is wrong today

### 2.1 The shell eats the first screen
`AppShell.tsx:164` renders the whole navigation as a card above the content on every viewport below `lg` (1024).

| Measurement | Phone 375 | iPad portrait 768 | Laptop 1440 |
|---|---|---|---|
| `/my-work` content starts at | 700 px | 700 px (nav card 577, then an 860 px rail) | 87 px |
| `/incidents`, `/assessments` | 700 px | 700 px | 87 px |
| `/mission-center` map top / list top | 912 / 1502 | 890 / 1644 | 235 / 234 (side by side) |

iPad portrait is the worst-served width: the sidebar appears at `lg` and every two-pane grid waits for `xl` (1280), so 768 gets the phone's stacked nav *and* stacked panels. On a phone the map and the list are never visible together.

**The measured content width matters for every desktop composition in this plan.** At 1440 with the 256 px sidebar pinned, `main` measures **1097 px** wide (`brief-core.md`, `desktop_1440x900./my-work.mainRect.w`). Any composition that needs more than 1097 px does not fit on the machine most office staff use. §6.2 sizes the three-region form against that number instead of against the viewport.

### 2.4 Worst audit findings
**S4** stacked nav card below `lg` · **S4** GISA pixel canvas (clips under ~545 px) · **S4** Approve/Finalize/Request-revision/Remove fire on a single 28 px click with no confirmation and no success message · **S4** intake requires hand-typing lat/lon to six decimals with `type=number`, which hides the minus key on iOS while every California longitude is negative · **S4** terrain toolbar `max-w-[calc(100%-360px)]` resolves to zero width at 343 px.
**S3** `WorkflowTreeView` and `getWorkflowTree` are written, tested and **never mounted** — no screen shows where an incident sits or who owns it · **S3** four competing homes (`/` role-aware, Login → `/my-work`, 404 → `/mission-center`, `RoleRoute` denial → `/submissions`, a page deliberately given no nav entry) · **S3** the map viewport resets to California on every 60 s poll and every keystroke · **S3** triage pre-checks the nearest group within 25 miles and writes the association *before* the disposition, irreversibly, with errors rendering behind the overlay.

### 2.5 Two defects the first plan missed

**The reporter's loop has no return leg.** A coordinator can send a report back (`POST /incidents/{id}/request-revision`, `incidents.py:1354-1401`) and the reporter can answer it — `PATCH /incidents/{id}` (`maintenance_resubmit_incident`, `incidents.py:1408`) exists, is scoped to the reporting user, and **rejects any change outside the requested fields** (`incidents.py:1444-1478`). The web client offers no screen that calls it. The coordinator's "Ask the reporter for more information" disposition therefore commits into a dead end on the web, and the reporter's third top task has no destination. §7.19 gives it one; no backend work is required.

**Two things the plan assumes have nowhere to live.** `parse_user_metadata` (`backend/app/user_metadata.py:44-48`) returns exactly `{district, office_code, office_location}` and drops every other key, and `routes/auth.py:39` returns that object verbatim — so a feature flag cannot ride on `/auth/me` metadata (§8 now uses a build-time Vite variable instead, matching the existing `web/src/config.ts:15-22` pattern). And nothing in the product stores a per-user UI preference: theme and density live in `localStorage` via `UiSettingsContext`, so on a shared field iPad the last person's theme wins and every "once per account" promise misfires. §11 adds **B11** for that.

### 2.6 Vocabulary
Eleven terms rate high or very-high confusion. The three that cause the measured failures: **Status vs Stage vs State** (three parallel machines; web shows `status` and never `current_stage`, mobile shows raw stage text); **Field worker** (legacy `FIELD_WORKER` means *Staff*; "Maintenance Field Worker" means the *reporter* — the plain reading is the opposite of the code, and the header prints the code at `AppShell.tsx:157`); **Assessment / Submission / GISA / Draft** (one object with four names; "Draft" means three different things; "submitted" is both a submission status and an assessment state). A fourth, quieter one: the backend renders **"Maintenance Field Worker"** for the reporter inside the progress tree (`workflow_tree.py:40`) while every other surface in this plan says **"Maintenance Field Reporter"** — §9.1 and §11 close that.

## 3. Design principles

| # | Principle | Statement | Code-review test |
|---|---|---|---|
| P1 | **One place per incident** | Everything about an incident lives at `/incidents/:id`; assessment, form, evidence, site and history are tabs. Legacy record URLs still resolve — they render the same case file on the right tab. | A new top-level `<Route>` rendering a record detail that is not `/incidents/:id`, `/assessments/:id`, `/submissions/:id` or `/event-groups/:id` is rejected. |
| P2 | **One banner, one button, no redirection** | Every object page and tab opens with one Next-step banner: plain status, holder (named person, or "you"), one sentence on what happens after, one primary button. **No page ever tells the user to act somewhere else.** | Grep for "in My Work", "performed from", "actions live in" in user copy — any hit fails. Assert exactly one `data-primary-action` per route. |
| P3 | **Place before ids** | Every row, banner, title and popup leads with the incident title and the shared location string. Numeric ids appear once, muted, last. Codes never appear. | Rendering `#{id}` before the title, or interpolating `office_code`/`current_stage`/`state`/a role code/a section key into user text, fails. All go through the labels module. |
| P4 | **Only what this page decides** | Three tiers of disclosure and only three: expandable row, drawer/sheet, overflow menu. Never nest beyond two levels; never put units, requirements or a disabled reason behind hover. | **Max 5 facts per row; max 4 data columns at `md`, 6 at `xl`, cards below `md`.** A row's single action column holds controls, not facts, and does not count against the column budget — but there is at most one of it and it never carries text a user must read. Any `title=` carrying information not also visible fails. |
| P5 | **Compose per width, never shrink** | Tailwind's stock breakpoints; each gets a *designed* composition. Below `md`: bottom bar, single pane, sheets. `md`: 80 px rail, single pane. `lg`+: two panes. A third region is **container-queried at 1240 px of workspace width**, never assumed from a breakpoint. | `nestedScrollRegions === 0` below `lg`, `<= 1` at `lg`+ (plus at most one horizontal chip strip, §6.3). `mainContentStartsAtPx <= 64` below `md`, `<= 120` above. New `max-h-[Npx] overflow-auto` without `data-scroll-region` fails. |
| P6 | **Consequence before commit, receipt after** | Anything that changes ownership, notifies someone or cannot be undone opens a sheet naming the target and person, stating the consequence, holding *that action's* note, focusing Cancel when destructive; success leaves a persistent notice saying what happened and where it went. | Every call site of `delegateBranch`, `assignSeniorEngineer`, `assignEngineer`, `addAssignment`, `submit`, `review`, `resolve`, `triage`, `resubmitIncident`, `disableUser`, `resetPassword`, `deleteSubmission`, `grantAccess`, `revokeAccess`, `publishVersion` must sit inside a confirm surface and pass a message to the notice region. |
| P7 | **Never disable a primary silently** | A primary is never disabled without its reason in the same sentence position. Where the block is incompleteness, the button stays live and opens a completeness sheet linking to what is missing. Where the block is policy (you cannot disable your own account), the reason is rendered as visible text beside the control. | `disabled` on a primary without an adjacent visible reason fails. `Send for review` is never `disabled`. |

**Review authority follows the assessment's routing path — it is neither a job nor an assignment.** On the **branch route** the named branch chief (`assessments.branch_chief_user_id`) reviews; on the **senior engineer route** an office chief of the assessment's office reviews. Nothing else grants it. The `REVIEWER` account role keeps operational read and loses `/submissions/{id}/review|approve|reject`; `REVIEWER`/`APPROVER` assignment rows remain as history, rendered *"Former reviewer — no approval authority."* `CONSULTED` survives as the for-information assignment.

**Two permission changes, stated rather than assumed.** §7.6's `canEdit` replacement widens the GISA form to canonical `GEOTECH_ENGINEER` and `GEOTECH_SENIOR_ENGINEER` accounts (twelve `require_roles(["FIELD_WORKER","ADMIN"])` guards in `main.py` and two in `photos.py` become `GISA_AUTHOR_ROLES`) and narrows it to the assignee. Office scoping becomes load-bearing for the first time: a chief or senior engineer with no `metadata.office_code` can neither review nor be assigned — which is why §7.16 gains an Office field.

Office scoping becomes load-bearing *and* becomes real data. The office a chief belongs to moves from `users.metadata_json.office_code` to `org_user_profiles.office_id`, resolved by one helper used by both readers so no chief loses a queue mid-migration. Nothing about who may review changes: branch route, the named branch chief; senior-engineer route, an office chief of that assessment's office. Deactivating an office in admin never revokes review authority on work already routed to it.

## 5. Information architecture and navigation

### 5.1 The model — four destinations, max

1. **Home** — what needs me. Landing page for **every** role, reporters included. Count badge.
2. **Records** — look something up. Three segments: **Incidents · Event Groups · Assessments**. No badge. For reporters this is a single list titled "My reports".
3. **Map** — where is it (renamed from Mission Center). Not shown to reporters.
4. **One role-specific fourth**: **Admin** (Users · Road inventory · Routing), or **Terrain** for Staff and senior engineers, the only personas whose top task begins there.

Plus an avatar menu (name, humanised roles, theme, Settings, Sign out) and a **Help button in the same header slot on every page** (WCAG 3.2.6). Everything else stops being a destination: assessments and forms are case-file tabs; Terrain opens from the case file for everyone else; Settings lives in the avatar menu; Access sharing is a flow route off the Technical form (§7.21).

**Two contradictions resolved.** *Case-file wanted Event Groups as a filter; task-first wanted a Records segment* — **Records wins**: the new-user judge overruled its own preferred proposal, because the coordinator's first decision at triage is an event decision and Event Group carries the highest confusion rating. *The field judge wanted Records cut to Incidents + Event Groups; the domain judge required an assessment-shaped office view* — **both are satisfied**: Assessments is a Records *segment*, but selecting a row **opens the case file's "Who has it" tab**. There is exactly one record detail surface in the product.

### 5.2 The case file — five tabs

Cut from case-file's seven by folding Report into Overview and Site into Photos, and relabelled by job because "Assessment" and "Form" are the app's worst vocabulary collision.

| Tab | Holds | Backend behind it |
|---|---|---|
| **Overview** | Next-step banner, the field report as filed (description, times, reporter, photos, RI match), the 9-step progress rail, key facts, Event Group chip | `incidents`, attachments, workflow tree |
| **Who has it** | Route (branch or senior engineer) and why; office, branch chief or senior engineer, assignee; **who reviews this assessment, by name**; hand-off note; pipeline with per-step timestamps; the role's routing action | `assessments`, `assessment_assignments`, events |
| **Technical form** | Section task list with completion and autosave; the reviewer's quoted comment when returned; read view for everyone else | `submissions`, `submission_gisa*` |
| **Photos & site** | Every photo/video/document from the report and every form with telemetry badges; site map with pin and drawn area; saved cross sections; 3D on request | attachments, geometry, cross sections |
| **History** | One merged humanised timeline of incident, assessment and submission events, notes quoted in full, actors named | `workflow_events`, `assessment_events` |

**Phone tab strip: three visible plus More** — Overview · Who has it · Form · **More** (Photos & site, History). Five labels do not fit 375 px, and a scrolling tab strip is unacceptable on the primary field device. The tab's primary action is always in the sticky bottom bar, never in the strip.

## 6. Responsive layout system

### 6.1 Breakpoints — Tailwind's, unchanged

**We do not redefine `sm`/`md`/`lg`/`xl`/`2xl`.** Three of four judges rejected the proposed 480/600/840/1200/1440 remap: it silently reinterprets **136 existing utilities across ~50 screens** in one atomic release, in a codebase that just shipped a redesign and runs no DOM tests in CI, for no user-visible gain. `index.css` has no `@theme` block; adding one to override breakpoints would be Phase 0's largest regression risk. Instead: document the ERIS window classes as *names for the stock numbers*, export them from `web/src/ui/breakpoints.ts` for `matchMedia`, and use **Tailwind v4 container queries** for everything panel-internal — a pane's own width, not the viewport, decides whether a pipeline is horizontal, a column is visible, or a third region exists.

|---|---|---|---|

### 6.3 Touch and density rules

≥24×24 px with 8 px spacing everywhere (SC 2.5.8 floor); **≥44×44 px hit area under `@media (pointer: coarse)`** via `pointer-coarse:min-h-11 min-w-11` on Button, nav items, row actions, chips, checkboxes (wrapped in a 44 px label), ArcGIS `view.ui` widgets, 3D controls, pipeline steps, dialog closes. Rows 48 px coarse / 40 px fine. **Nothing essential below 12 px — including navigation labels**, which is why the iPad rail label is 12 px and not 10 px. **16 px phone inputs** to stop iOS zoom.

**No hover-only affordances.** The justification is *not* that Tailwind scopes `hover:` inside `@media (hover:hover)` — the real hover affordance in this codebase is hand-written CSS at `index.css:132` (`.attachment-tile:hover .attachment-tile-actions`), which no Tailwind scoping touches. It already ships a `@media (hover: none)` override at `index.css:138-142` plus `:focus-within`, so the pure-touch case is handled today. **The residual case is the hybrid pointer**: an iPad with a Magic Keyboard trackpad reports `hover: hover` while the user taps the glass, and gets the fade-in behaviour with no hover. The rule is therefore: any control that must be discoverable is always visible, and `:hover` only ever *emphasises* something already rendered. Links are underlined.

Selected state is never colour alone (`aria-current` / `aria-pressed` plus a glyph or 2 px border). **Every drag has a tap alternative** — the form canvas drag is deleted; cross-section points are removable and zoomable from the Points list; the pane handle answers ArrowLeft/Right. **Maps on coarse pointers require gesture opt-in** so a scrolling finger is never captured.

**Bars never stack.** Bottom bars are `min-h-14 pb-[env(safe-area-inset-bottom)]`. A route shows **either** the bottom nav bar **or** one sticky action bar, never both, at any width:
- On `:id`, flow and section routes the nav bar is replaced by a back control in the header plus the action bar.
- **On a nav destination that needs an action bar — `/terrain` is the only one (§7.15) — the action bar replaces the nav bar** and the header's left slot becomes a Home control. Its height is `--action-bar-h: 44px`.
- Every full-height container subtracts every bar above and below it. `/map`: `calc(100svh - var(--header-h) - var(--segment-h) - var(--bottom-nav-h) - env(safe-area-inset-bottom))`. `/terrain`: `calc(100svh - var(--header-h) - var(--action-bar-h) - env(safe-area-inset-bottom))`.
- The nav bar hides **only when the soft keyboard is up**, detected as `window.visualViewport.height` shrinking by more than 120 px — never on focus alone, because on iPadOS with a hardware keyboard the visual viewport does not shrink and the navigation would disappear for no reason.

**Scroll regions.** Outside the page scroll, a screen may have **at most one vertical scroll region** — sticky rail, sheet body, dialog body, or a table's horizontal wrapper — **plus at most one horizontal scroll-snap chip strip**. Every one carries `tabIndex={0}`, an edge fade and `data-scroll-region` (`"pane"` or `"chips"`). A chip strip is allowed only if it is ≤48 px tall and **every destination in it is also reachable from a non-scrolling control on the same screen** — the form hub's section list for the section chip strip, the More menu for the case-file cross-link row. The `max-h-[860/760/520/420px]` caps are deleted. At 320 px and 400 % zoom, headers, filters, fields, dialogs and the Next-step banner never scroll horizontally.

**One `MapView` per mounted map, never two on one screen.** The Map destination keeps a single `MapView` alive in its layout route across list/detail changes. Embedded maps — the case-file site map, the triage candidates map, the photo map — each own their own view, created on mount and destroyed on unmount. Where a flow would put two on screen at once (the triage candidates map over a case file already showing its site map), the flow is a full-screen route below `md` and, from `md`, a dialog that detaches the underlying view (`view.container = null`) while it is open and reattaches on close. ArcGIS views are never shared between two mounted panes.

### 6.4 Tailwind v4 implementation notes

- No `@theme` breakpoint block; add `web/src/ui/breakpoints.ts` for `useBreakpoint()`, used by ArcGIS sizing and the Map \| List control. Never key layout to a device name.
- **`@container`** on the detail pane, supporting pane, dialog body, toolbar, table wrapper and **the form workspace** (the `@[1240px]` third-region rule); children sized with `@sm:`…`@5xl:` (pipeline `flex-col @2xl:flex-row`; priority-2 columns `hidden @3xl:table-cell`). One panel component then works at 360 px in a sheet, 440 px docked and full width on a phone.
- **Measured CSS variables**, all set on `:root` by one `ResizeObserver` hook with static fallbacks: **`--header-h`** (56), **`--bottom-nav-h`** (56), **`--action-bar-h`** (44), **`--segment-h`** (44), `--panel-h`. Used by `top-`, `scroll-mt-` and every `calc(100svh - …)`. **Delete the magic `top-[82px]`** (`AppShell.tsx:166`).
- **`svh` for map and scene containers, `dvh` for everything else** that must survive the URL bar and keyboard; add `viewport-fit=cover`. Debounce the ArcGIS resize handler at 150 ms regardless.
- Overflow hygiene: `min-w-0` on every flex child holding text or a table; `minmax(0,1fr)` never bare `1fr`; delete fixed min-widths above ~277 px (`min-w-[280px]` search, `min-w-72` card, `min-w-[520px]` chart).

- Scroll-spy uses `IntersectionObserver` with fixed anchors — a scroll-position implementation jitters on iPad Safari.
- **Delete on landing**: `submissionLayoutModel.ts`, `useSubmissionDashboardLayout.ts`, the `aside lg:hidden` nav card (`AppShell.tsx:164`), **the `product-card overflow-hidden` wrapper around `<main>`'s children (`AppShell.tsx:185`) — it defeats `position: sticky` for every sticky index, sub-toolbar and action bar in §6**, **the `max-w-[1900px]` shell cap (`AppShell.tsx:140,163,189`), replaced by the 1600 px cap §5.3 specifies**, the nested `max-h` caps, `min-w-[74px]` pipeline steps, `max-w-[calc(100%-360px)]`, the 1200 px colgroup, and the raw role codes at `AppShell.tsx:157`.

### 9.3 Onboarding

**No welcome tour, coach-mark carousel or video** (`brief-research.md:37`: front-loaded tours are skipped, not remembered, and show no measured performance gain). Staff rotate and touch ERIS only during events. The budget goes into six things.

1. **First-run "How your work flows" card**, once per account, dismissible and recallable from Help: 3–5 steps in the plain status vocabulary with the user's own step highlighted (*Coordinator: Report filed → **You review** → GeoTech assesses → Approved → Resolved*). Admins get "Where things get stuck". Reporters get *File → Coordinator reviews → **They may ask you for more** → Accepted*.
2. **The Help panel**, same header slot on every page (SC 3.2.6): How your work flows · Words used in ERIS · Contact GeoTech support. Side sheet on desktop and iPad landscape, bottom sheet on phones, never covering the action bar.
3. **Empty states carry the teaching** — why it is empty, what will appear, one action. This replaces onboarding prose repeated on every item.
4. **Just-in-time definitions.** The first time a session shows *Event Group*, *ERIS number*, *Route this assessment*, *Returned for changes* or *GeoTech office*, the term renders with a dotted underline and a tap/click info popover — **never hover-only**, because the primary device is an iPad. **Status chips are tap-to-open on detail pages and inside the Next-step banner only.** They are **inert text inside list rows**, because §6.2 makes the whole card one ≥64 px link and a tappable popover trigger nested inside a link is ambiguous to tap and invalid to nest. In lists the definition lives on **one info button per group header**, outside every card.
5. **Exactly two coach marks**, once per account. The coordinator's first review flow: ***"Pick the site this report belongs to — nothing is saved until you press Accept and send."*** The Staff member's first form: *"Sections can be completed in any order; your work autosaves."* Nothing else earns one. **Why these two are exempt from the finding in `brief-research.md:37`:** that finding is about *front-loaded* tours and carousels shown before the user has a task. These are single, in-context marks that appear inside the one irreversible flow in the product at the moment the user is in it, and each states a fact the interface cannot show — that nothing has been written yet, and that order does not matter. If the Phase 2 walkthrough shows either is ignored, it is deleted rather than reworded.
6. **Success confirmations as onboarding.** Every action produces a persistent notice naming the object, the new state and where it went — *"Assessment for ERIS no. 24-0417 handed off to Maria Chen. It has left your queue and is now under Records › Assessments."* — with "Open it" and Undo where the backend allows. People learn the flow by doing it.

**Where the "once per account" state lives.** Items 1 and 5, the dismissal memory in §9.4 item 10, the Records-assessments first-visit hint, the pane width, the list-pane state, theme and density all need a per-user store. **There is none today** — `UiSettingsContext` writes `localStorage`, so on the shared field iPads named in open question 7 the last person's state wins and every "once per account" promise misfires. **B11** adds `GET`/`PUT /users/me/ui-preferences` and `last_sign_in_at`; until it lands, all of these degrade to `localStorage` and the plan says so in the UI ("Stored in this browser only", §7.18).

**Rotating-staff return path**: an account idle 60+ days sees the card once more, driven by `last_sign_in_at` from B11. "Recently done by me (7 days)" stays collapsed on Home so people can see where their last actions went.

### 9.4 Contextual help — the rules

1. **Nothing essential lives in a tooltip.** Units, required markers, formats and *why a button is disabled* are visible text. Tooltips carry only backend names staff already know, and icon buttons (which also need `aria-label`).
2. **Every disabled primary states its reason in the same sentence position** — "Hand off — choose a branch chief first". Never a hover-only explanation. Where policy blocks the action (§7.16 Disable), the primary stays live and the reason is text beside it.
3. **One Next-step card per object**, with the reviewer's comment quoted inside it when present, clamped to four lines with a link to the full text.
4. **Definitions on first use**, opened by tap/click/Enter — never hover, and never nested inside a link (§9.3 item 4).
5. **A Help button in a fixed slot on every page**, deep-linked to the current page's section.
6. **Forms**: label + visible hint (unit as a suffix outside the input, an example value) + on-blur format checks for typed measurements only; completeness on "Save and mark complete" and Send, with an error summary that links to each field and moves focus. Errors are fix-oriented — "Enter the post mile as a number, e.g. 12.40" — never "invalid". Entered text and photos are **never** cleared on error.
7. **Success and failure appear where the user is looking**: errors inside the open sheet, notices anchored to the panel that changed, a bottom toast on phones. Every notice names the object.
8. **Status is never colour alone**: chip = light background + dark text + short label; markers = shape + label; the current step says "Now" and carries `aria-current="step"`.
9. **Autosave and dirty state are visible** and politely announced; explicit Save remains; leaving with unsaved changes asks first.
10. **Explanatory banners show once**, then collapse to a one-line hint with an info icon; dismissal is remembered per account once B11 lands, per browser until then.
11. **Codes are demoted, not deleted**: a "Technical details" disclosure per record holds raw ids and enums for support calls — including "GISA" and "Mission Center". Nothing else prints an enum.
12. **Backend vocabulary appears once per surface** as a parenthetical for the transition — "Route this assessment (Delegate)", the one transition whose backend name still differs — removed after one release once training catches up.

## 10. Accessibility — WCAG 2.2 AA (California / Section 508 / AB 434)

This is the definition of done, not a phase.

- **Target size (SC 2.5.8)** — ≥24×24 px with 8 px spacing, and **≥44×44 px hit area under `@media (pointer: coarse)`**: rail cards, row actions, filter and role chips, tile buttons, ArcGIS `view.ui` widgets sized via CSS, 3D controls, pipeline steps, dialog closes, "Remove file". *Baseline: 120 controls under 40 px on `/submissions/3` alone — see §12 for why the threshold is stated explicitly.*
- **Text contrast, light theme (SC 1.4.3)** — `--brand #1f9bd1`, `--good #1d9d5d`, `--bad #d14b54` on white or `--panel-soft` measure roughly 3.0–4.0:1 and **fail 4.5:1** for 11–13 px badge text and for white text on `.btn-brand`. **Add per-theme text tokens** `--good-text` (≥ `#157a47`), `--bad-text` (≥ `#b0303a`), and a `--warn` base plus `--warn-text` — **`index.css` defines no `--warn` today**, so the warn pair is two new tokens, not one.
  **On `--brand-text`: the token already exists under another name.** `index.css:18` defines `--brand-ink: #0e4c6a` in the light theme — the exact value v1.0 proposed for a new `--brand-text`. But `:35` defines `--brand-ink: #e4f0ff` in dark and `:52` `#063e42` in coastal, i.e. the token means *ink on a brand surface*, which is a different job from *brand-coloured text on a page surface*. **Do not overload it.** Add `--brand-text` as a separate token whose light value is `#0e4c6a` (matching today's `--brand-ink`), and document the two roles side by side in the token file so the next person does not merge them.
- **Dark theme** — verify `--line #233a61` on `--panel #0f1d33` reaches 3:1 for field boundaries (SC 1.4.11); it likely fails. Add `--line-strong` for input borders and focus rings. **Coastal** — brand/good/bad pass; do not use `--muted #4f7280` on `--panel-soft` below 12 px. **The contrast report is generated from the token file at build time** so a theme change cannot regress silently.
- **Minimum text size** — nothing essential below 12 px, **navigation labels included** (baseline 74 tiny nodes on the form page, 23 on `/my-work`); body 14 px, cells 13–14 px, 16 px phone inputs; everything reflows at 200 % zoom without clipping.
- **Status not by colour alone (SC 1.4.1)** — chips carry text; markers encode by shape + label with a legend of only visible symbols; the current step says "Now".
- **Focus visible and not obscured (SC 2.4.7, 2.4.11)** — a 2 px `--brand` ring on every control, rail card and link; sticky headers and action bars must not cover the focused element (`scroll-margin-top` = header height; no nested fixed-height scrollers that hide focus).
- **Keyboard path for every map (SC 2.1.1)** — every map has a same-page list with the same records and filters; row selection highlights the marker and vice versa; the container has `tabIndex={0}` and an `aria-label`; popups open with an explicit **Open**; **no action is marker-only**.
- **Keyboard path for canvas and 3D** — the profile SVG is focusable with ArrowLeft/Right (+Shift ×10) and tap-to-pin; control points are editable from a list and coordinates can be typed; the `SceneView` is progressive enhancement with the elevation table and 2D map as its equivalent; Escape returns focus to the toolbar (no ArcGIS keyboard trap).
- **Pointer gestures and dragging (SC 2.5.1, 2.5.7)** — mouse-only drag/resize is removed; every remaining drag has a single-pointer and keyboard alternative; pinch/pan on an inline map never traps page scroll on touch.
- **Reflow (SC 1.4.10)** — at 320 px and 400 % zoom, headers, filters, fields, dialogs and the Next-step card never scroll horizontally. Only whole tables, maps and the one allowed chip strip may, inside `overflow-x-auto` containers with `tabIndex={0}`, a visible cut-off and an `aria-label`.
- **Reduced motion (SC 2.3.3)** — honour `prefers-reduced-motion` for map `goTo` (`{animate:false}`), marker highlight, sheet and drawer transitions, skeleton shimmer and the 3D fly-to.
- **Live regions** — one polite region for autosave state, queue reloads and success notices; `role="alert"` for errors; `aria-busy` while a record loads. Never announce per keystroke.
- **Names and roles** — every input, select and search has a programmatic label; icon buttons have `aria-label`; tab strips use `role="tablist"` with `aria-selected`; tables have `<caption>` and `aria-sort`; dialogs use `role="dialog"` + `aria-modal` + labelled-by, focus trap, Escape and focus return (the existing `ModalDialog` does this — the Save cross-section and Aerial capture dialogs must adopt it).
- **Page identity (SC 3.2.3–3.2.6)** — `document.title` per route; skip-to-content; `aria-current="page"`; a breadcrumb on record pages; **Help in the same place on every page**.
- **Forms (SC 3.3.1–3.3.3, 3.3.7 Redundant Entry)** — inline errors via `aria-describedby` + `aria-invalid`; a linked error summary on submit; the technical form is **pre-filled from the incident** (D/C/R/PM, coordinates, dates) so nothing already entered is re-typed; the reporter's update flow (§7.19) shows current values rather than asking for them again; tri-state radios start unselected and stack on narrow screens.
- **Print (`brief-research.md:64`)** — the print stylesheet is part of the accessibility surface, not decoration: printed tri-state answers are words, printed links carry their label, and the print header repeats the record identity on every page.
- **Session and timeouts (SC 2.2.1, 2.2.5)** — warn before expiry; preserve URL and unsaved draft across re-authentication; keep the token on 5xx and show a retry (§7.20).
- **No hover-only affordances**; links underlined; every `title=` value duplicated visibly or in Technical details. The hybrid-pointer case (iPad + trackpad) is covered by making discoverable controls unconditionally visible, not by a media query (§6.3).
- **Media** — thumbnails carry alt text from caption and section ("Photo 3 — slope face, looking north"); video and PDF have a visible "Open in new tab" fallback where inline preview fails on iOS; legends are real text.
- **Testing gate** — `axe` (wcag2a, wcag2aa, wcag22aa) on every route in all three themes at 375, 768, 1024 and 1440 px and at 200 %/400 % zoom; a manual keyboard walkthrough of the four core paths (coordinator review, hand-off/assign, Staff send, reviewer decide) on desktop and iPad with VoiceOver.

## 11. Roadmap

### The team the numbers assume

**73 working days of calendar, seven phases.** The unit is a working day for a team of:

- **2 front-end engineers**, working in parallel on separate components within a phase;
- **2 backend engineers full-time for Phase 1**, then **1 backend engineer at roughly a third of their time** from Phase 2 on, working ahead of the phase that consumes their item;
- **1 designer at half time** for specs, copy and review;
- **1 QA engineer at half time from Phase 3**, when the flagged form work starts.

That is **137 front-end engineer-days and 37.75 backend engineer-days**. v1.0 quoted 66 calendar days without stating a team, which made its Phase 0 (10 days against 21 component-days of its own scope) impossible to check. The table below shows the arithmetic per phase: component-days from §8, plus the page assembly those components feed, plus the QA and accessibility work, divided by two front-end engineers. Each phase after Phase 0 is independently shippable because **routes never move**.

## 13. Open questions for the owner

1. **Does approval close the incident?** **The sign-off half is closed by the owner: there is no sign-off.** Approval ends the assessment and the incident stays open until `/incidents/{id}/resolve`, with the workflow tree showing Resolution as CURRENT owned by the assignee. The plan surfaces that honestly with "Ready to close out". What remains open is only the narrower question — **should approval auto-resolve?** If so, that is a one-line backend change and it removes a step from every journey.
2. **Can more than one assessment exist per incident?** The case file assumes one. If a re-assessment can be opened, "Who has it" needs a selector and the progress rail needs a branch.
3. **Web photo upload.** Is the submission attachment endpoint callable from the browser origin today (CORS + presign), or is that a backend task (B8)? Until it is, the plan states in writing that photos come from the mobile app — and the Staff first-day journey still ends one step short on an iPad browser.
4. **Event Group vs Project on mobile.** Web will say Event Group only. Do we change the mobile strings in the same release, or ship "Event Group (formerly Project)" for one release?
5. **The legacy `REVIEWER` account role — closed by the owner.** Keep the accounts, keep operational read, remove all review authority; existing `REVIEWER`/`APPROVER` assignment rows become history and are never rewritten. Review authority follows the assessment's routing path (§4).
6. **District coordinator routing gaps.** Coverage becomes a table (`org_coordinator_coverage`), so a district with no active coordinator is a query, surfaced on the Coverage tab (§7.22) and the System-health strip. What remains open is only whether ERIS should *refuse* such a report or notify a fallback.
7. **Theme and density on shared field iPads** persist per browser, not per account, so the last person's theme wins. B11 moves them to the user record — confirm that is wanted before Phase 6 spends 1.5 backend days on it.
8. **How long should "Recently done by me" stay?** The plan uses 7 days; coordinators reviewing weekly may want 14 or 30. B12 takes the window as a parameter, so this is a copy decision, not a rebuild.
9. **Do we keep three themes?** Each triples the contrast verification surface. Dropping Coastal would measurably cut Phase 6.
10. **The 60-day return path** needs a `last_sign_in_at` the client can read. B11 adds it to `/auth/me` — confirm the field exists on the user record, or it becomes a schema change.
11. **Emergency escalation.** Nothing marks an incident urgent, so every queue here sorts by age. If Caltrans wants a severity flag driving order, that is a backend field and a new chip — decide it before Phase 1 sets the sort.
12. **Should a non-assigned Staff member keep the edit access they have today?** `canEdit` (`SubmissionDetailPage.tsx:162`) is currently *any* `FIELD_WORKER` or `ADMIN` on a `DRAFT`/`REJECTED` submission, with no assignment check. §7.6 narrows it to the assigned Staff member. Two Staff in one branch covering for each other rely on the current behaviour, and it is unverified whether the server rejects the narrowed case. Confirm the intent, and whether the server should enforce it.
13. **How big is the 3D terrain payload?** The load prompt should name a real figure. No evidence file measures it, so v1.1 removed the "about 20 MB" that v1.0 shipped as user-facing copy; Phase 4 measures it on the field iPad and puts the number back.
14. **Are incidents closed at triage without an assessment public?** Default no, behind a settings flag. Viewers then see a gap between the incident count and the public count.
15. **Is a viewer statewide or scoped?** Default statewide; a scoped viewer needs an org link and a rule for the unscoped case.
16. **Does a viewer get raw photo bytes, or only the rendered record?** The attachment gates are per-file with no assessment context, so granting them is a separate decision from granting the record.

> Questions 14–16 **ship decided**, with the defaults the organization-model design states: closed-at-triage incidents are not public, viewer read is statewide, and viewers do get the photo bytes and attachment downloads of an approved record. Each is a settings or allow-list change, not a code change, if the owner decides otherwise. [`docs/org-model.md`](../org-model.md) holds the operator-facing consequence of each, and the full list of fifteen organization-model questions lives with that design.
